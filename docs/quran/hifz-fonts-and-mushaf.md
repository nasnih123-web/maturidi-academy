## ۱. اصل pairing: مصحف = script + font + layout + numbering، یک مجموعهٔ هماهنگ

یک پروفایل مصحف چهار جزء دارد که باید از یک خانواده باشند؛ تغییر یکی بدون سه تای دیگر، مصحف دیگری نمی‌سازد:

| جزء | یعنی چه |
|---|---|
| **corpus / script** | متن کلمه‌به‌کلمه با رسم‌الخط و segmentation همان مصحف (مثلاً Uthmani حفص با تطویل، یا Indopak با ی/ک فارسی‌شکل) |
| **font** | فونتی که دقیقاً همان script را رندر کند (فونت Unicode با فونت glyph-based قابل‌تعویض نیست؛ فونت نستعلیق با فونت نسخ قابل‌تعویض نیست) |
| **layout** | شکست صفحه/خط و تراز هر خط (صفحه‌بندی همان چاپ: ۶۰۴ صفحهٔ مدینه با ۶۱۰ صفحهٔ IndoPak یکی نیست) |
| **numbering** | نظام شماره‌گذاری آیهٔ همان روایت (حفص ۶٬۲۳۶؛ ورش ۶٬۲۱۴؛ دوری ۶٬۲۱۸ — از `surah.json` همان مصحف) |

**صرف تغییر CSS/فونت، پشتیبانی IndoPak محسوب نمی‌شود** — متن، شکل حروف، segmentation و layout باید با هم عوض شوند.

### ۲٫۴ سوییچ «indopak» فعلی در خواننده — فقط فونت، نه مصحف

کد فعلی (`apps/web/components/QuranReader.tsx:342,550` و `apps/web/app/[locale]/globals.css:1111-1115`):

- `type ScriptId = 'uthmani' | 'indopak'` و `scriptClass = script === 'indopak' ? 'quran-script-indopak' : 'quran-script-uthmani'` — با توضیح صریح در کامنت: **«(typeface only)»**.
- کلاس `.quran-script-indopak` فقط `font-family` را عوض می‌کند: `"Noto Nastaliq Urdu", "Alvi Nastaliq", "Noto Naskh Arabic", serif` با `line-height: 2.6` — **فونت‌های دستگاه کاربر** (device fonts)؛ هیچ فایل نستعلیقی در مخزن نیست و هیچ `@font-face`ای برای آن‌ها تعریف نشده است.
- متن همان Tanzil حفص/عثمانی می‌ماند، شکست خط‌ها همان Madinah V2 می‌ماند، segmentation همان Tanzil می‌ماند، صفحه‌بندی همان ۶۰۴ صفحه می‌ماند.

**نتیجه:** کاربر با انتخاب indopak، متن عثمانی حفص را با یک فونت نستعلیقِ دستگاه (اگر نصب باشد) می‌بیند — نه رسم‌الخط Indopak، نه صفحه‌بندی ۶۱۰ صفحه‌ای قدرة‌الله، نه نشانه‌های وقف Indopak. این **پشتیبانی IndoPak نیست** و نباید در UI یا مستندات چنین معرفی شود. مسیر درست در §۵ آمده است.

- صفحات SVG هر پنج روایت از quran-ws زنده خوانده می‌شوند (۶۰۴ صفحه برای هر مصحف، شمارهٔ صفحه per-mushaf).

| نشانهٔ پایان آیه | عدد عربی (١ ٢ …) — **بدون U+06DD** |

**پس فایل ما فقط «شکست خط» می‌دهد، نه layout کامل مصحف.** برای رندر صفحهٔ چاپی کافی است (متن آماده + نوع خط)، ولی برای highlight کلمه‌ای، tap روی کلمه، یا نمره‌دهی حفاظ در سطح کلمه کافی نیست — آن کارها به شناسهٔ کلمه (QUL `word_index` یا تقسیم Tanzil) نیاز دارند.

### ۴٫۳ نمونهٔ صفحهٔ ۱ در برابر مثال مستندات QUL

مثال `docs/mushaf-layout` برای ص ۱، هشت خط با بازه‌های شناسهٔ کلمه می‌دهد: ۱–۵، ۶–۱۰، ۱۱–۱۷، ۱۸–۲۳، ۲۴–۲۹، ۳۰–۳۳، ۳۴–۳۶. هشت خط فایل ما دقیقاً همین بازه‌های کلمه را پوشش می‌دهند (بسمله + ۴ کلمه + نشانه؛ حمد + …؛ تا `وَلَا ٱلضَّآلِّينَ ٧`). **شکست خط‌های ما با Madinah V2 یکی است.**

### ۴٫۴ اختلاف‌ها (جایی که هست، QUL مرجع است)

| # | اختلاف | مرجع درست |
|---|---|---|
| ۱ | **رسم‌الخط متن یکی نیست.** فایل ما Tanzil است (`ٱلْعَـٰلَمِينَ` با تطویل)؛ script سازگار با layout دیجیتال‌خط (`digital-khatt-v2.json`) همان کلمه را `ٱلْعَٰلَمِينَ` (بدون تطویل) می‌نویسد؛ QPC Hafs آن را `ٱلۡعَٰلَمِينَ` می‌نویسد. شکست خط یکی است، حروف یکی نیستند | برای رندر «عین چاپ مدینه» باید script و فونت هم با layout جفت شوند (QPC Hafs script ‏۲۴۵ + layout ‏۱۰)، نه فقط شکست خط |
| ۲ | **تراز خط (centered) ثبت نشده.** در Madinah V2 خط‌های اول/آخر صفحه و خط‌های سربرگ/بسمله تراز وسط دارند؛ فایل ما هیچ پرچم ترازی ندارد و رندر باید آن را حدس بزند | QUL ‏`is_centered` در جدول `pages` |
| ۳ | **بازهٔ کلمه‌ای ثبت نشده.** فایل ما فقط بازهٔ آیه (`v`/`w`) دارد؛ برای highlight یا tap کلمه‌ای باید از متن، کلمات را دوباره شمرد — و شمارش Tanzil با شمارش QUL فرق دارد (سند همراه §۳٫۳) | QUL ‏`first_word_id` / `last_word_id` |
| ۴ | **نشانهٔ پایان آیه به شکل عدد ساده است** (بدون U+06DD)؛ در QUL نشانه یک «کلمه» با U+06DD است | تفاوت نمایشی؛ برای سازگاری با شناسه‌های QUL باید تبدیل شود |
| ۵ | **صفحه‌های دارای چند سربرگ سوره** (مثل ص ۶۰۴: اخلاص + فلق + ناس) در فایل ما درست آمده‌اند (۳ سربرگ + ۳ بسمله در ۱۵ خط) ✅ | — |

> احتیاط روشی: پیش‌نمایش متنی صفحهٔ ۱ در صفحهٔ منبع layout ‏۲۱ (Digital Khatt V2) در استخراج متن، خط‌ها را جابه‌جا نشان می‌دهد (هر کلمه یک لینک جداست و شکست خط در متن استخراج‌شده قابل‌اعتماد نیست). مقایسهٔ بالا فقط بر اساس **مثال کد مستندات QUL** و **جدول بازهٔ آیهٔ ابزار layout** انجام شده، نه پیش‌نمایش متنی.

### گام‌های لازم برای IndoPak واقعی (به ترتیب)

1. تعیین مجوز کتبی برای سه جزء (اسکریپت + فونت + layout) — هر سه فعلاً **نامشخص**‌اند.
2. انتخاب **یک** جفت مشخص (پیشنهاد: `qpc-nastaleeq.json` + فونت ۲۴۲ + layout ‏۱۲، چون layout ‏۱۲ منابع مرتبطش دقیقاً همان اسکریپت و فونت را نشان می‌دهد).
3. bundle هر سه جزء با هم + جدول تبدیل شناسهٔ کلمه به تقسیم Tanzil (برای اینکه حفاظ/ASR که روی Tanzil است، با کلمات Indopak قاطی نشود).
4. صفحه‌بندی ۶۱۰ صفحه‌ای جدا از ۶۰۴ صفحه‌ای حفص؛ ناوبری صفحه (`?view=page`) باید کلید پروفایل را همراه شمارهٔ صفحه بگرداند (مثل کلید مصحف در `quran-svg-page.ts`).
5. حذف یا بازنام‌گذاری سوییچ CSS فعلی تا وقتی پروفایل واقعی نیامده است (نام فعلی گمراه‌کننده است).

## ۷. موارد باز

1. **مجوز QUL** — تماس کتبی با Tarteel/QUL برای اسکریپت‌ها و فونت‌ها؛ تا آن زمان هیچ bundleای از QUL انجام نمی‌شود.
2. **اصلاح جدول §۲۰٫۲ سند مأموریت** — تفکیک شناسهٔ ابزار از شناسهٔ منبع؛ منبع دانلود Madinah V2 عدد **۱۰** است.
3. **ثبت دوبارهٔ provenance ‏WOFF2** — هش‌های واقعی §۳٫۱ را در `THIRD_PARTY_NOTICES.md` به‌روز کنید یا WOFF2ها را از روی TTFهای تأییدشده دوباره encode کنید.
4. **وزن‌های Cairo/Inter/Vazirmatn** — اگر وزن واقعی لازم است، فایل‌های وزن‌دار واقعی جایگزین کپی‌های یکسان شوند (اولویت پایین، مربوط به UI است نه قرآن).
5. **جدول تبدیل شناسهٔ کلمه** — پیش از هر استفاده از شناسه‌های QUL در حفاظ، جدول تبدیل QUL-id ↔ Tanzil-whitespace-index لازم است (۴٬۶۳۵ آیه شمار متفاوت دارند).
