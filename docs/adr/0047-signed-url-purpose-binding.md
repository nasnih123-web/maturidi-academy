# ADR-0047 — گره‌خوردن امضای URL دانلود به منظور + بررسی رکورد گواهی

## زمینه
امضای HMAC ارائه‌دهندهٔ محلی فقط روی `(key, exp)` بود و endpoint
`/api/v1/lms/certificates/download-by-ref` هر امضای معتبر را برای
هر کلیدی می‌پذیرفت — بدون احراز، بدون بررسی دیتابیس. نتیجه: URL
امضاشدهٔ یک فایل کتابخانه (یا هر جریان دیگر) در این endpoint کار
می‌کرد و هر کلیدی که برایش از هر جایی امضا صادر شده بود، به‌نام
«گواهی» خوانده می‌شد.

## تصمیم
- payload امضا به `(purpose, key, exp)` گسترش یافت و purpose در
  خود URL هم می‌آید (داخل HMAC است؛ دست‌کاری‌اش امضا را باطل
  می‌کند). منظورها: `library`، `lms-certificate`، و پیش‌فرض عمومی
  `download`.
- هر download-by-ref فقط امضای هم‌منظور خودش را می‌پذیرد.
- endpoint گواهی علاوه بر امضا، وجود رکورد `Certificate` با
  `pdf_storage_ref == key` را هم بررسی می‌کند (نبودش 404 با همان
  کد خطای مسیر احرازی). endpoint کتابخانه از قبل resolve رکورد
  داشت و حالا purpose هم می‌خواهد.
- مهاجرت URL ذخیره‌شده لازم نیست: URLها در DB ذخیره نمی‌شوند و
  عمرشان دقایقی است؛ URLهای پیش از تغییر تا انقضای طبیعی‌شان از
  کار می‌افتند.
- در provider S3، purpose بی‌اثر است (SigV4 خود MinIO ذاتاً به
  آبجکت گره خورده و دانلود از endpoint اپ نمی‌گذرد) — در docstring
  صریح شده است.

## پیامدها
- نشت یا جابه‌جایی URL بین جریان‌ها دیگر دانلود نمی‌سازد؛ تست
  منفی اصلی: امضای معتبر library برای کلید گواهی → 403.
- صداهای TTS و بیلدهای local که پیش‌تر URLشان به‌اشتباه به مسیر
  گواهی اشاره می‌کرد و فایل را به‌جای PDF سرو می‌کرد، حالا رد
  می‌شوند (آن مسیر در production روی S3 است و بی‌تأثیر می‌ماند).

## جایگزین‌های ردشده
- احراز هویت اجباری روی download-by-ref: قرارداد §۶ «امضا جای
  احراز» است (لینک برای اشتراک‌گذاری کوتاه‌مدت)؛ مشکل، نبود
  binding بود نه نبود session.
- کلید امضای جدا برای هر منظور: همان اثر با پیچیدگی مدیریت
  secret بیشتر؛ purpose داخل payload کافی است.
