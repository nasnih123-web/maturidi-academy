# ADR-0041 — یکپارچگی باکت بیلدها بین کالبک CI و API (FIX2-02)

- وضعیت: پذیرفته‌شده — ۲۰۲۶-۱۰-۲۳ (اصلاحیهٔ دوم ممیزی PR #16)

## زمینه
کالبک بیلد (B-01، ADR-0025) فایل‌ها را با Secretهای `BUILDS_S3_*` در
گیت‌هاب به باکت builds می‌فرستد، ولی سمت API ساخت URL دانلود و
`prune_releases` از `get_storage()` عمومی (باکت `S3_BUCKET`) استفاده
می‌کرد. هیچ چیزی در کد این دو کانفیگ را به هم گره نمی‌زد: اگر در یک
استقرار این دو باکت متفاوت بودند، دانلود و pruning بی‌صدا روی باکت
اشتباه کار می‌کردند و خطا فقط هنگام دانلود کاربر دیده می‌شد.

## تصمیم
1. **provider اختصاصی بیلدها:** `get_builds_storage()` در
   `app/core/storage.py` تنها نقطهٔ ساخت provider برای مسیر بیلدهاست و
   `builds_service` (ساخت URL و prune) فقط از همان استفاده می‌کند.
2. **قرارداد «همه یا هیچ» برای `BUILDS_S3_*`:** چهار تنظیم اصلی سمت API
   (`BUILDS_S3_ENDPOINT`/`ACCESS_KEY`/`SECRET_KEY`/`BUCKET`، با
   `ENDPOINT_PUBLIC` و `REGION` اختیاری) یا همه با هم تنظیم می‌شوند —
   دقیقاً برابر مقادیر GitHub Secrets، تا کالبک و API روی یک باکت
   باشند — یا هیچ‌کدام؛ در حالت دوم بیلدها همان باکت واحدِ storage
   عمومی برنامه (`S3_*`) را مصرف می‌کنند و کانفیگ دومی وجود ندارد.
3. **fail-fast در startup:** `validate_builds_storage()` از lifespan
   صدا زده می‌شود؛ کانفیگ ناقص (بعضی پر، بعضی خالی) یا قالب نامعتبر با
   `RuntimeError` واضح (بدون افشای secret) بوت را متوقف می‌کند.

## پیامدها
- ناسازگاری باکت دیگر «خرابی خاموش هنگام دانلود» نیست؛ یا استقرار از
  اول درست است یا اصلاً بالا نمی‌آید.
- استقرارهای ساده (یک MinIO، یک باکت) هیچ کانفیگ اضافه‌ای نمی‌خواهند.
- تست‌ها: واحدی برای هر سه حالت کانفیگ + یکپارچهٔ
  upload → signed URL → download → prune روی provider یکپارچهٔ پیش‌فرض
  (`tests/test_builds_storage_unification.py`).

## جایگزین‌های ردشده
- **الزام همیشگی BUILDS_S3_\* جدا:** برای استقرار تک‌باکتی اصطکاک
  بی‌دلیل می‌ساخت و احتمال خطای اپراتوری را بالا می‌برد.
- **هشدار لاگی به‌جای fail-fast:** همان کلاس «خرابی خاموش» بود که این
  یافته از آن آمده است.
