# ADR-0010 — فاز ۱۳: موتور همگام‌سازی آفلاین (بک‌اند)

> **وضعیت:** پذیرفته‌شده — فاز ۱۳ (Track 1: Backend)
> **تاریخ:** 2026-10-19

## زمینه

مشخصات فاز ۱۳ (بخش «موتور Sync») سه قاعدهٔ متفاوت برای سه نوع داده می‌خواهد:
دادهٔ ساده (پیشرفت، شمارش تسبیح) با max-wins/LWW؛ محتوای نوشته‌شدهٔ کاربر
(یادداشت آیه) بدون هیچ دورریزی بی‌صدا؛ حذف‌ها با tombstone بین دستگاه‌ها.
قرارداد §۱۵.۱۰ هر تغییر مدل داده/قرارداد API را منوط به ADR می‌کند.

## تصمیم‌ها

### ۱) سیاست تعارض به‌تفکیک نوع موجودیت (نه یک قانون برای همه)

| موجودیت | سیاست | چرا |
|---|---|---|
| `user_progress` | max-wins: `position_seconds` → بیشینه؛ `status` → پیشرفته‌ترین (`completed > in_progress > not_started`) | اسکالر یکنوا؛ ادغام قطعی و بدون ابهام |
| `dhikr_daily_counts` | max-wins روی `total_count` به‌ازای هر روز/ذکر | شمارش تجمیعی؛ بیشینه هرگز داده کم نمی‌کند |
| `user_ayah_notes` | نسخه‌بندی خوش‌بینانه (`version` + `base_version`)؛ اگر `base_version < version` فعلی و محتوا متفاوت باشد → **تعارض**: نسخهٔ سرور نگه داشته می‌شود، نسخهٔ کلاینت در `conflict_records` ذخیره می‌شود، رویداد `sync.conflict_detected` | محتوای نوشته‌شدهٔ کاربر؛ هیچ نسخه‌ای بی‌صدا دور ریخته نمی‌شود |

حل تعارض (`POST /sync/conflicts/{id}/resolve`): `keep_local` (نسخهٔ دستگاه
اعمال می‌شود) | `keep_remote` (نسخهٔ سرور می‌ماند) | `merged` (payload
ادغام‌شدهٔ کاربر). هر سه رویداد `sync.conflict_resolved` می‌سازند.

قرارداد نام‌گذاری: در `conflict_records`، «local» = نسخهٔ دستگاهی که دیرتر
push کرد و بازنده شد؛ «remote» = نسخهٔ فعلی سرور که برنده شد.

### ۲) چرا tombstone (و نه حذف فیزیکی)

حذف فیزیکیِ فوری برای دستگاهی که آفلاین است قابل انتشار نیست: وقتی دستگاه
دوم بعداً pull می‌کند، ردیفی برای «نبودن» وجود ندارد تا بفهمد باید نسخهٔ
محلی را پاک کند. پس حذف = `sync_tombstones` (ماندگار، هرگز زود پاک نمی‌شود)
+ ردیف `delete` در `sync_changelog` که pull آن را منتشر می‌کند.

انحراف آگاهانه از متن تسک: یکتایی tombstone به‌صورت
`(user_id, entity_type, entity_id)` است نه فقط `(entity_type, entity_id)` —
چون `entity_id`هایی مثل `lesson_id` در `user_progress` بین کاربران یکتا
نیستند. این تقویتِ مشخصات است، نه تضعیف.

سیاست برخورد upsert با tombstone:
- `base_version > tombstone.version` → احیا (tombstone برداشته، upsert اعمال می‌شود).
- وگرنه برای یادداشت → `conflict_records` (باز هم بدون دورریز بی‌صدا)؛
  برای اسکالرها → `rejected` با `detail=tombstoned` (حذف برای اسکالر معتبر است).

حذفِ مستقیم از API عادی (مثل `DELETE /quran/notes/{id}`) هم tombstone
می‌سازد تا pull دستگاه‌ها کامل بماند.

### ۳) ژورنال تغییرات + کرسر به‌ازای دستگاه

`sync_changelog` (ستون `seq` خودافزای سراسری) تنها منبع pull است؛
`GET /sync/pull?cursor=N&device_id=` فقط ردیف‌های `seq > N` همان کاربر را
می‌دهد و `device_cursors(user_id, device_id)` را جلو می‌برد. ثبت در ژورنال
از یک تابع مشترک (`record_entity_change` در سرویس sync) انجام می‌شود که
سرویس‌های quran و lms روی جهش‌های مستقیم (آنلاین) هم صدا می‌زنند — منطق
ادغام تکراری نشده (§۱۵.۲)، فقط «ثبت تغییر» مشترک است. pull افزایشی است
(فقط بعد از کرسر).

### ۴) idempotency بازپخش

`sync_operations.client_op_id` یکتاست؛ نتیجهٔ هر op در ستون `result` ذخیره
می‌شود و بازپخش همان `client_op_id` دقیقاً همان پاسخ را بدون اعمال دوباره
برمی‌گرداند. (تفاوت §۴: این idempotencyِ «درخواست» است، جدا از `event_id`
رویدادهای دامنه.)

### ۵) offline-pack: امتیازدهی ساده و صادقانه

`GET /sync/offline-pack` سه منبع را با امتیاز ثابت مرتب می‌کند:
شروع‌شده (درس‌های دارای `user_progress`: ‏۱۰۰ برای in_progress، ‏۹۰ برای
completed) > دنبال‌شده (آیتم‌های منتشرشدهٔ کتابخانه از اساتید دنبال‌شده: ‏۷۰)
> محبوب (‏۵۰). «محبوب» پروکسی recency است (جدیدترین‌های منتشرشده) چون
شمارندهٔ دانلود/بازدید در این فاز وجود ندارد — هیچ MLای ادعا نشده.

### ۶) اعلان‌ها: `web_push` کانال جدا + کلیدهای staged

- `notification_preferences.channel` حالا `web_push` را هم به‌عنوان مقدار
  مجزا از `push` (FCM موبایل) می‌پذیرد — تغییر مقداری است، نه اسکیما؛
  migration لازم نیست.
- کلیدهای جدید `platform_settings` (فقط در رجیستری، staged و خالی، هرگز
  هاردکد — §۱۵.۳): `push.fcm_server_key` (secret)،
  `push.vapid_public_key` (string)، `push.vapid_private_key` (secret).

## پیامدها

- مثبت: هر دستگاه با `device_id` پایدار می‌تواند آفلاین کار کند و با
  push/pull همگام شود؛ تعارض یادداشت هرگز داده از دست نمی‌دهد؛ pull
  افزایشی است (فقط بعد از کرسر).
- منفی/موقت: ژورنال `sync_changelog` هرس (prune) نمی‌شود — برای فاز ۱۳ کافی
  است؛ با رشد داده باید سیاست نگهداری (مثلاً نگه‌داری ۹۰ روزه + حداقل seq
  فعال دستگاه‌ها) اضافه شود.

## یادداشت صداقت (از متن مشخصات فاز ۱۳)

تست شرایط شبکهٔ واقعی (قطع‌وصل، throttle، payload حجیم، retry/backoff سمت
کلاینت، conflict حین pull ناقص) در این فاز در سطح unit/integration پوشش داده
شده، نه با شبیه‌ساز شبکهٔ واقعی. اگر بعد از این فاز باگ sync ادامه‌دار دیده
شد، یک دور جداگانهٔ «سخت‌سازی sync» طبیعی و موردانتظار است — این یکی از
سخت‌ترین حوزه‌های واقعی مهندسی نرم‌افزار است و یک فاز آن را صددرصد حل
نمی‌کند. موارد باز برای آن دور: هرس ژورنال، فشرده‌سازی/صفحه‌بندی pullهای
خیلی بزرگ، backoff نمایی سمت کلاینت، و تست دستی با Network Link Conditioner.

## جایگزین‌های ردشده

- **LWW سراسری برای همه:** برای یادداشت کاربر غیرقابل‌قبول است (دورریز بی‌صدا).
- **اشتقاق pull از `updated_at` جدول‌ها:** با حذف فیزیکی و ساعت‌های ناهماهنگ
  دستگاه‌ها شکننده است؛ ژورنال صریح (`seq`) قطعی و تست‌پذیر است.
- **CRDT تمام‌عیار:** برای سه موجودیت ساده، هزینهٔ پیاده‌سازی/نگهداری بیش از
  سود است؛ سیاست‌های بالا همان تضمین‌های لازم را با کد ساده می‌دهند.

## تکمیلی هماهنگ‌کنندهٔ فاز (integration)

پس از اتمام هر سه ترک، این موارد افزوده شد تا شکاف‌های بین ترک‌ها بسته شود:

- `GET /api/v1/sync/devices` (owner-scoped) و `GET /api/v1/admin/sync/devices`
  (مجوز `sync.manage`) — اجتماع `user_devices` و `device_cursors`؛ دستگاهی که
  فقط sync کرده ولی توکن ثبت نکرده هم دیده می‌شود. داشبورد CRM از نسخهٔ ادمین
  استفاده می‌کند.
- `POST /api/v1/users/me/devices` — ثبت/چرخش توکن FCM (upsert)؛ خود توکن هرگز
  در audit log ذخیره نمی‌شود (فاز ۰ §۱۴).
- `POST|DELETE /api/v1/users/me/web-push/subscriptions` و
  `GET /api/v1/notifications/web-push/vapid-key` — اشتراک VAPID مرورگر، جدا از FCM.
- جدول‌های `user_devices` و `web_push_subscriptions` (migration دوم فاز).
- مجوز `sync.manage` در seed.

تست‌ها: ۱۷ تست sync (شامل سناریوهای بالا) + کل سوئیت ۲۶۶ سبز.
