# ADR-0003: اسکیمای تنظیمات polish — نوع json، فونت، revalidation

- وضعیت: پذیرفته‌شده
- تاریخ: 2026-10-19
- میل‌استون: polish — Track A (بک‌اند)

## زمینه

قرارداد فاز ۰ §۱۵.۱۰ می‌گوید تغییر قرارداد API/مدل داده بدون ADR ممنوع است.
میل‌استون polish به ۸ کلید جدید در `platform_settings` نیاز دارد (ذرات،
فونت هر لوکیل، اسلات‌های خانه، متن هیرو) که هیچ‌کدام در ۴ نوع موجود
(`secret | string | localized | uuid`) جا نمی‌شوند، و وب باید بتواند
تنظیمات را per-request با revalidation بخواند (تسک #۳).

## تصمیم

۱. **نوع پنجم `json`**: هر مقدار JSON-serializable؛ برای کلیدهای polish
   اعتبارسنج اختصاصی (canonical output) و برای بقیه فقط serializable بودن.
   افزودنی است — ۴ نوع قبلی و همهٔ کلیدهای موجود دست نخورده‌اند.
۲. **کلیدهای جدید** (مستندات کامل: `docs/settings-schema.md`):
   `particles`، `fonts.fa/ar/en`، `home.sections`، `hero.fa/ar/en`.
   همه non-sensitive، همه از همان envelope رمزنگاری و همان API ادمین.
۳. **revalidation**: کش درون‌فرایندی موجود حفظ شد (hot-reload فاز ۲/ADR-002)
   ولی TTL آن به ۶۰ ثانیه محدود شد (`SETTINGS_CACHE_TTL`)؛
   `GET /settings` از قبل `updated_at` هر آیتم و `version` کلی را برمی‌گرداند و
   هر نوشتن (از جمله فونت) نسخه را بالا می‌برد.
۴. **فونت‌ها** زیر `apps/api/static/fonts/<locale>/` ذخیره و از `/static`
   سرو می‌شوند (mount در `main.py`)؛ دایرکتوری runtime است و در `.gitignore`.
   حذف = بازگشت به `null` (فونت داخلی).
۵. **dark mode**: در بک‌اند هیچ کلید/منطقی نداشت — تغییری لازم نبود.

## پیامدها

- مثبت: CRM می‌تواند ذرات، فونت، ترتیب بخش‌ها و متن هیرو را بدون ری‌استارت
  و بدون migration تغییر دهد؛ وب با `version` revalidate می‌کند.
- منفی: `/static` فعلاً فقط فونت دارد؛ اگر مدیای دیگری اضافه شد باید
  همان قرارداد (اعتبارسنجی §۷ + audit) را بگیرد.

## جایگزین‌های ردشده

- جدول جدا برای فونت/هیرو: سربار مدل اضافه؛ settings همین قرارداد
  کش/نسخه/audit را دارد (همان استدلال ADR-002).
- حذف کامل کش: ریسک رگرسیون در hot-reload فاز ۲؛ TTL ۶۰ ثانیه تعادل امن است.
