# ADR-0019: مرزهای ماژول — عدم تفکیک models.py و انضباط import بین دامنه‌ها

- وضعیت: پذیرفته‌شده
- تاریخ: 2026-10-19
- تصمیم‌گیرنده: Track C (بازبینی معماری)

## زمینه

`apps/api/app/models/models.py` یک فایل ۲۳۲۴ خطی با ۹۷ مدل SQLAlchemy است که
۱۰۳ فایل از `app/modules/*` از آن import می‌کنند. سؤال بازبینی: آیا باید به
ماژول‌های جدا (مثلاً `models/auth.py`، `models/content.py`، …) تفکیک شود؟

تحلیل گراف import (اسکریپت بازبینی Track C):

- `models.py` فقط از `app.core.database` (کلاس `Base`) به‌علاوهٔ stdlib و
  SQLAlchemy وارد می‌کند — **هیچ import برگشتی از `app.modules` ندارد.**
- در سطح فایل، بین فایل‌های `app/modules/*` **هیچ چرخهٔ import واقعی نیست.**
  تنها یال مشکوک در سطح دایرکتوری `auth ↔ content` است که در سطح فایل چرخه نیست:
  `auth/service.py` فقط ثابت `LEGAL_TEXT_VERSION` را از `content/legal.py`
  می‌گیرد و `content/legal.py` یک برگِ بدون هیچ import از `app` است؛
  جهت معکوس (`content/router.py` ← `auth/dependencies`) به فایل دیگری اشاره دارد.
- یال‌های بین‌دامنه‌ای محدود و موجه‌اند: `auth` (وابستگی‌های احراز هویت)،
  `content ← workflow` (ماشین حالت واحد §۹)، و چند ارجاع سرویسی هدفمند.

## تصمیم

1. **`models.py` تفکیک نمی‌شود.** دلایل:
   - هیچ چرخه‌ای برای شکستن وجود ندارد؛ تفکیک، مسئله‌ای را حل نمی‌کند.
   - هر جابه‌جایی کلاس بین فایل‌ها ریسک بی‌صدا تغییر دادن metadata
     (نام جدول/constraint/identifier) را دارد که با قرارداد §۱۲ (forward-only)
     و سازگاری DB ناسازگار است؛ منفعتش فقط «زیبایی فایل کوچک‌تر» است.
   - ۱۰۳ نقطهٔ import باید بازنویسی می‌شدند بی‌آنکه رفتار عوض شود.
2. **انضباط مرزی با تست نگه داشته می‌شود** (`apps/api/tests/test_module_boundaries.py`):
   - گراف import سطح-فایلِ `app/modules/*` باید بدون چرخه بماند؛
   - `models.py` فقط مجاز است از `app.core.database` (و stdlib/third-party) وارد کند؛
   - `content/legal.py` باید برگ بماند (بدون هیچ import از `app.*`) تا یال
     `auth → content` هرگز به چرخهٔ واقعی تبدیل نشود.
3. اگر روزی تفکیک لازم شد، پیش‌شرطش **تست migration** است که ثابت کند نام
   جدول‌ها، constraintها و identifierها بی‌تغییر مانده‌اند — نه قبل از آن.

## پیامدها

- مثبت: ریسک صفر برای سازگاری دیتابیس؛ مرزها به‌جای حدس، با تست کنترل می‌شوند.
- منفی: فایل models.py بزرگ می‌ماند؛ ناوبری با جست‌وجوی نام کلاس انجام می‌شود
  (نام کلاس‌ها یکتا و صریح‌اند).

## جایگزین‌های ردشده

- **تفکیک به `models/<domain>.py` با re-export در `models/__init__.py`:**
  ریسک واقعی (metadata/alembic/import-order) در برابر منفعت صرفاً زیبایی‌شناختی —
  خلاف اصل «ماژول سالم را بدون دلیل واقعی بازنویسی نکن» (قرارداد §۱۵.۱).
- **لایهٔ واسط `app/modules/<x>/models.py` جدا:** دو منبع حقیقت برای یک جدول
  می‌ساخت و قرارداد «مدل typed هر دامنه» (§۹.۵) را تضعیف می‌کرد.
