# ADR-0001: گذرگاه رویداد بلادرنگ با fallback حافظه‌ای

**وضعیت:** پذیرفته‌شده — فاز ۲ (2026-10-18)

## زمینه

قرارداد §۴ می‌گوید dispatcher رویدادهای پردازش‌نشده را از **دیتابیس** می‌خواند
(نه فقط اتکا به Redis) و از طریق Redis Pub/Sub به دروازهٔ WebSocket می‌رساند.
اما روی ماشین توسعه/تست، Redis و Docker در دسترس نیست؛ سیستم باید بدون Redis
هم بالا بیاید و تست‌ها سبز بمانند.

## تصمیم

1. `EventBus` یک ABC است با دو پیاده‌سازی: `RedisBus` و `InMemoryBus`.
   انتخاب در startup خودکار است: اگر `ping` به Redis موفق بود → Redis،
   وگرنه با **یک خط لاگ هشدار** → حافظه‌ای.
2. منبع حقیقت همیشه جدول `domain_events` است (outbox)؛ bus فقط «حمل» می‌کند.
   اگر InMemoryBus پیام را گم کند، رویداد در DB می‌ماند و dispatcher دوباره
   تلاش می‌کند — durability از DB می‌آید، نه از bus.
3. تلاش مجدد با backoff نمایی (`2^retry_count` ثانیه، سقف ۵ دقیقه) بدون ستون
   جدید — فقط با `created_at` و `retry_count` موجود؛ بعد از ۵ شکست `failed_at`
   ثبت می‌شود (dead-letter قابل مشاهدهٔ ادمین).
4. احراز هویت WebSocket فقط با JWT معتبر؛ کانال‌های `admin.*` نیازمند مجوز
   `realtime.admin` (همان join نقش‌ها، نه enum). بازپخش `last_event_id` از DB
   و مرتب بر اساس `created_at` است، نه از حافظه.

## پیامدها

- روی dev/CI بدون Redis همه‌چیز کار می‌کند؛ روی production با Redis مقیاس‌پذیر است.
- InMemoryBus تک‌فرایندی است: با چند instance API، هر instance فقط رویدادهایی
  را که dispatcher همان instance خوانده به کلاینت‌های خودش می‌رساند.
  روی production حتماً Redis باید بالا باشد (در `docker-compose.yml` هست).
- ترتیب بازپخش بر اساس `created_at` است؛ در صورت تساوی میکروثانیه‌ای، ترتیب
  دقیق تضمین نمی‌شود (مستند شده در `realtime.py`).

## جایگزین‌های ردشده

- **اتکای صرف به Redis Pub/Sub بدون polling دیتابیس:** خلاف §۴؛ با قطعی Redis
  رویداد گم می‌شد.
- **حذف fallback و اجباری‌کردن Redis در dev:** تست‌ها و توسعهٔ سبک را غیرممکن
  می‌کرد؛ خلاف «بدون Docker هم کار کند».
- **ستون `next_retry_at` جدید:** migration اضافه بدون نیاز واقعی؛ backoff با
  فیلدهای موجود محاسبه می‌شود.
