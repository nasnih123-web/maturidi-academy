# قرارداد مهندسی — آکادمی ماتریدی

> **وضعیت:** الزام‌آور برای همهٔ فازها (۰ تا ۱۷)
> **نسخه:** ۱.۰ — فاز ۰
> **قانون طلایی:** هر نشست ایجنت، قبل از هر تغییری، به‌ترتیب این‌ها را می‌خواند:
> ۱) همین سند (`docs/engineering-contract.md`)، ۲) همهٔ ADRهای مرتبط در `docs/adr/`،
> ۳) وضعیت واقعی فعلی ریپازیتوری، ۴) آخرین قرارداد پذیرفته‌شدهٔ API/رویداد/دیتابیس.
> هیچ‌وقت فرض نکن ریپو دقیقاً طبق سند پیش رفته — اول کد واقعی را ببین.

این سند چیزی نمی‌سازد که کاربر ببیند؛ قراردادهایی می‌سازد که هر فاز بعدی
**مجبور** است رعایت کند تا ۱۸ فازِ دستِ ۱۸ نشستِ جداگانه، هرکدام معماری خودشان را اختراع نکنند.

---

## ۱) قرارداد API

- هر endpoint یک OpenAPI schema کامل دارد — خودکار از FastAPI + Pydantic v2، **دستی ننویس**.
- پاکت خطای یکدست در کل پروژه:
  ```json
  {"error": {"code": "...", "message": "...", "details": {}}, "request_id": "..."}
  ```
- صفحه‌بندی: cursor-based برای مجموعه‌های بزرگ (offset ساده با رشد داده کند می‌شود).
- هدر `Idempotency-Key` اجباری برای عملیات حساس (پرداخت، هر نوشتن مالی).
- زمان: در دیتابیس همیشه UTC؛ در API همیشه ISO 8601؛ فقط در UI محلی‌سازی می‌شود.
  تاریخ هجری از یک لایهٔ انتزاعی تبدیل عبور می‌کند، نه محاسبهٔ پراکنده.
- نسخه‌بندی از امروز: `/api/v1/`. هر endpoint منسوخ با هدر `Sunset` مشخص می‌شود، نه حذف ناگهانی.

## ۲) احراز هویت و مجوزدهی

- Access token کوتاه‌مدت (۱۵ دقیقه) + refresh token با **rotation** (هر استفاده، توکن قبلی باطل و جدید صادر می‌شود) + امکان revoke دستی.
- هش رمز عبور: **Argon2id**.
- جدول `sessions`: نشست‌های فعال هر کاربر (دستگاه/IP/آخرین فعالیت). «خروج از همهٔ دستگاه‌ها» یک اقدام واحد است.
- `password_reset_tokens` و `phone_verification_codes`: یک‌بارمصرف، انقضای کوتاه.
- Rate limiting سراسری روی login/register (نه فقط مسیرهای AI)؛ قفل موقت بعد از تلاش‌های ناموفق پیاپی؛ CAPTCHA روی ثبت‌نام.
- **RBAC واقعی — نه enum روی کاربر.** چهار جدول:
  `roles(id, name)`، `permissions(id, key)` — مثل `fatwa.approve` و `content.publish` —
  `role_permissions(role_id, permission_id)`، `user_roles(user_id, role_id)`.
  جدول `users` **هیچ ستون `role`ای ندارد**؛ نقش همیشه از `user_roles` خوانده می‌شود تا دو منبع حقیقت با هم تناقض پیدا نکنند.
- **2FA = TOTP** (نه پیامکی — پیامک در برابر SIM-swap ضعیف‌تر است)
  + کدهای بازیابی یک‌بارمصرف (قابل ابطال/صدور مجدد)
  + ثبت‌نام 2FA برای `admin`/`super_admin` **اجباری** است — بدون آن وارد CRM نمی‌شوند.
  گم‌کردن دستگاه احراز هویت فقط با کد بازیابی یا فرایند کنترل‌شدهٔ ادمین ارشد حل می‌شود.

## ۳) معماری Secrets

- کلید رمزنگاری‌ای که مقادیر حساس `platform_settings` را رمز می‌کند، **در همان دیتابیس یا سرور نگه‌داری نمی‌شود** —
  از متغیر محیطی / secrets manager جدا تزریق می‌شود. اگر کلید و مقدار رمزشده یک‌جا باشند، امنیت واقعی وجود ندارد.
- جریان درست: `اپلیکیشن → secrets manager/env → کلید رمزنگاری → مقدار رمزشده در DB`
- **نسخه‌بندی کلید (key rotation):** هر مقدار رمزشده یک `encryption_key_version` کنار خودش دارد؛
  اگر کلید عوض شود، مقادیر قدیمی با کلید نسخهٔ قدیم قابل رمزگشایی می‌مانند تا به‌مرور بازرمزنگاری شوند.
- برای CI: `GitHub Secrets → pipeline → build امضاشده` — **هرگز secret داخل ریپو.**

## ۴) قرارداد رویداد دامنه (الگوی outbox)

جدول `domain_events`:

| ستون | توضیح |
|---|---|
| `event_id` | pk، UUID — هویت خودِ رویداد |
| `idempotency_key` | nullable، یکتا وقتی مقدار دارد — کلید idempotency درخواست/command مبدأ (مفهومی جدا از `event_id`) |
| `aggregate_type`, `aggregate_id` | موجودیت مبدأ |
| `event_type`, `payload` (jsonb), `schema_version` | محتوای رویداد |
| `source_client` | کلاینت مبدأ |
| `created_at`, `processed_at` (nullable) | زمان‌بندی |
| `retry_count`, `failed_at` (nullable) | مدیریت خطا |

- **تفاوت حیاتی:** هدر `Idempotency-Key` (قرارداد API) جلوی اجرای دوبارهٔ یک **درخواست/command** را می‌گیرد؛
  `event_id` هویت خودِ **رویداد** است که consumer برای دوبار-پردازش‌نکردن چک می‌کند. برای پرداخت (فاز ۱۵) این تفاوت حیاتی است.
- Redis Pub/Sub به‌تنهایی durable نیست. dispatcher رویدادهای پردازش‌نشده را از **دیتابیس** می‌خواند (نه فقط اتکا به Redis)،
  با backoff تلاش مجدد می‌کند و بعد از N شکست به صف **dead-letter** می‌فرستد که ادمین می‌بیند.
- Consumerها **idempotent** هستند — پردازش دوبارهٔ یک event نباید اثر تکراری بگذارد (چک `event_id` پردازش‌شده).

## ۵) معماری صف کار (ARQ)

صف‌های جدا به‌ازای نوع کار، هرکدام concurrency/retry جدا:

| صف | کاربرد |
|---|---|
| `critical` | پرداخت — بالاترین اولویت |
| `ai` | فتوا/دستیار صوتی — محدودتر، چون هزینه‌بر است |
| `media` | STT/TTS/OCR/تبدیل ویدیو |
| `telegram` | بات تلگرام و درون‌ریزی |
| `notifications` | ایمیل/پیامک/پوش |
| `analytics` | رویدادهای تحلیلی |

## ۶) معماری ذخیرهٔ فایل

- انتزاع `StorageProvider` — امروز MinIO، فردا هر S3-سازگار، **بدون تغییر کد بقیهٔ پروژه**.
- آبجکت‌های خصوصی (مثل `scholars_only`) با **signed URL** با انقضای کوتاه سرو می‌شوند، نه URL عمومی قابل‌حدس.
- محدودیت حجم به‌ازای نوع فایل؛ multipart upload برای فایل‌های حجیم.

## ۷) امنیت آپلود فایل

(حیاتی برای درون‌ریزی تلگرام و آپلود CRM)

- اعتبارسنجی پسوند + MIME + **magic-byte** (نه فقط پسوند — قابل جعل است).
- اسکن ویروس (ClamAV خوداستقرار).
- پاکسازی نام فایل؛ محافظت در برابر image-decompression bomb؛
  بررسی امنیتی PDF (بدون اجرای JavaScript جاسازی‌شده).

## ۸) معماری جست‌وجو

- جست‌وجوی واژگانی (PostgreSQL FTS + pg_trgm) **جدا** از جست‌وجوی معنایی (pgvector).
- تجمیع‌کننده هر دو را ترکیب می‌کند:
  `score = lexical + semantic + popularity + freshness`

## ۹) حاکمیت محتوا — یک موتور گردش‌کار واحد

یک state machine مشترک برای **همهٔ** انواع محتوا (فتوا، کتابخانه، صفحات CMS، پست‌های اجتماعی...):

```
draft → in_review → approved → published
                    ↘ rejected / archived
```

نه گردش‌کار جدا برای هر ماژول — یک پیاده‌سازی واحد.

### ۹.۵) قرارداد سراسری مدیریت محتوا و توزیع (Content Control Contract)

هر نوع محتوای قابل‌نمایش/انتشار باید داشته باشد: شناسهٔ دامنه، نوع محتوا، وضعیت گردش‌کار،
مالک/ایجادکننده، نسخه، زبان‌ها، تاریخ ایجاد/به‌روزرسانی، سیاست دسترسی.
CRM از طریق **adapter** آن را مدیریت می‌کند، نه با کپی‌کردن منطق دامنه.

- **Placement:** اتصال هر محتوا به یک یا چند surface/slot:
  `homepage.section`, `page.section`, `banner_area`, `scholar_profile`,
  `library_collection`, `quran_context`, `dashboard`, `widget`, `telegram`, ...
  با `sort_order`، شرط مخاطب، زمان شروع/پایان، locale و فعال/غیرفعال.
- **Distribution Policy:** کانال‌های `web`, `mobile`, `desktop`, `telegram`, `ai_knowledge`,
  `search`, `embed` (و بعداً بقیه) می‌توانند مستقل از انتشار اصلی روشن/خاموش یا زمان‌بندی شوند؛
  انتشار در یک کانال ≠ انتشار خودکار در همهٔ کانال‌ها.
- **Telegram policy:** هر نوع محتوا سیاست `never / manual_approval / auto_publish / scheduled` دارد؛
  جلوگیری از انتشار تکراری، template/caption قابل‌تنظیم، کانال مقصد مشخص، ثبت audit،
  امکان لغو/حذف پیام منتشرشده در صورت امکان provider.
- **AI policy:** محتوا مشخص می‌کند برای کدام کاربردهای AI مجاز است
  (`fatwa`, `assistant`, `quiz`, `verification`, `semantic_search`)؛ پیش‌فرض `none` مگر اجازهٔ صریح.
- **Preview:** هر تغییر قبل از انتشار باید در زبان/جهت لازم و روی surface مقصد قابل پیش‌نمایش باشد.
- **Schedule:** انتشار/عدم‌انتشار می‌تواند زمان‌بندی شود؛ schedule باید timezone-aware باشد.
- **Versioning:** انتشار نسخهٔ جدید، نسخهٔ قبلی را حذف نمی‌کند؛ rollback از طریق workflow ممکن است.
- **No future-FK coupling:** هیچ فازی برای جدول دامنه‌ای که در فاز بعد ساخته می‌شود، migration با FK فیزیکی نمی‌سازد؛
  اتصال بین فازها با abstraction/reference یا migration همان فاز انجام می‌شود.
- **اصل ضد-جدول-غول‌پیکر:** هیچ «جدول generic content» برای جایگزینی همهٔ domain modelها ساخته نمی‌شود.
  هر دامنه (صفحه، فتوا، کتاب، صوت، ویدیو، دوره، قرآن...) مدل typed خودش را حفظ می‌کند.

### ۹.۶) حاکمیت منابع AI و تحقیق خارجی

سه کلاس منبع: `internal_approved`، `trusted_external`، `public_web`.

- **Fatwa mode:** فقط محتوای داخلی تأییدشده با provenance فقهی مجاز است؛ وب عمومی به‌صورت پیش‌فرض **ممنوع**.
- **General Assistant:** محتوای داخلی تأییدشده + (در صورت فعال‌سازی ادمین) منابع خارجی مورداعتماد؛ منبع هر پاسخ قابل مشاهده است.
- `trusted_external_sources`: حداقل `name`, `base_url/domain`, `enabled`, `allowed_paths`, `priority`,
  `citation_required`, `last_checked_at`, `crawl/search_policy` — فقط `super_admin` می‌تواند تغییر دهد.
- تحقیق وب عمومی **پیش‌فرض خاموش** است؛ فقط از طریق provider/adapter مشخص، با allowlist، rate limit،
  timeout، ثبت URL و timestamp، و برچسب «منبع خارجی».
- محتوای خارجی هرگز بدون ثبت provenance وارد Knowledge Base داخلی نمی‌شود و
  محتوای crawlشدهٔ خارجی برای پاسخ فتوای رسمی به‌صورت خودکار trusted نمی‌شود.

## ۱۰) پایهٔ AI برای Production

- نسخه‌بندی prompt و مدل؛ لاگ کامل هر retrieval (کدام chunkها بازیابی/استفاده شدند)؛ الزام استناد به منبع.
- محافظ توهم: اگر در RAG نبود، صراحتاً «نمی‌دانم».
- **چهار لایهٔ همیشه مجزا:** دستورات سیستم ≠ قوانین ایمنی ≠ محتوای بازیابی‌شدهٔ معتمد ≠ ورودی کاربر —
  هرگز در یک context بدون مرز قاطی نمی‌شوند.
- RAG فقط محتوای `approved`/`published` را می‌بیند (طبق گردش‌کار §۹)، هرگز `draft`.
- مدل fallback در صورت خطای provider؛ timeout/retry مشخص؛ لغو stream وسط پاسخ ممکن باشد.
- لاگ مصرف token/هزینه به‌ازای کاربر.

## ۱۱) رصدپذیری (از همین فاز — نه فاز ۱۷)

- لاگ ساختاریافته (JSON) → Loki
- متریک → Prometheus + Grafana
- ردیابی توزیع‌شده → **OpenTelemetry** (از همین فاز)
- خطا → Sentry
- هشدار بحرانی → بات تلگرام مدیریتی

## ۱۲) استراتژی migration

- نام‌گذاری یکدست؛ فقط **forward-only** (rollback با migration جدید نوشته می‌شود، نه برگشت جادویی).
- پشتیبان‌گیری اجباری پیش از هر migration مخرب.
- migrationها در CI تست می‌شوند.

## ۱۳) استراتژی تست (از همین فاز)

هرم کامل: unit، integration، **contract** (بین هر کلاینت و API)، component، E2E.
به‌علاوه تست‌های خاص این پروژه (در فازهای مربوطه): تست قواعد فقهی، golden test ماشین‌حساب‌ها،
ارزیابی کیفیت RAG، تست replay وبهوک پرداخت، تست تعارض sync آفلاین.
اسکن امنیتی (**Semgrep** + dependency scan) در CI از همین فاز — نه موکول به فاز آخر.

## ۱۴) استاندارد audit log

هر رکورد: `actor_id, actor_type, action, entity_type, entity_id, old_values(jsonb),
new_values(jsonb), ip, user_agent, request_id, created_at` —
روی فتوا، پرداخت، کاربران، نقش‌ها، تنظیمات، محتوا، تلگرام، پیکربندی ماشین‌حساب.

**حذف/پنهان‌سازی secrets اجباری:** رمز عبور، توکن، کلید API، session تلگرام و هر مقدار احراز هویتی
**هرگز** در `old_values`/`new_values` ذخیره نمی‌شوند — فقط ثبت می‌شود که «این فیلد تغییر کرد»
(مثلاً `{"field": "telegram_session", "changed": true}`)، نه مقدار واقعی قبل/بعد.

## ۱۵) قوانین سخت کدنویسی برای ایجنت — هرگز نقض نکن

1. ماژول سالم را بدون دلیل واقعی بازنویسی نکن.
2. منطق کسب‌وکار را تکرار نکن؛ فقط در لایهٔ service.
3. هیچ secretای هاردکد نکن.
4. هیچ متن قابل‌مشاهدهٔ کاربر را هاردکد نکن — همیشه `LocalizedText`.
5. هیچ قاعدهٔ فقهی را هاردکد یا از دانش عمومی خودت استنتاج و منتشر نکن.
6. از لایهٔ دامنه/سرویس عبور نکن؛ router هرگز مستقیم به دیتابیس دسترسی ندارد.
7. API بدون type/schema صریح نساز.
8. برای سبزکردن CI، تست را غیرفعال یا حذف نکن.
9. در مسیر عملیاتی (production path) دادهٔ mock نگذار.
10. بدون ثبت یک ADR کوتاه در `docs/adr/`، قرارداد مهندسی، قرارداد API، مدل داده یا schema رویداد را تغییر نده.
11. تغییر breaking در قراردادهای موجود ممنوع است مگر با migration و نسخه‌بندی صریح
    (مثلاً `/api/v2/` جدید در کنار `v1`، نه بازنویسی `v1` موجود).

## ۱۶) تعریف «انجام‌شده» (Definition of Done) — برای هر فاز، بدون استثنا

یک فاز کامل نیست مگر همهٔ این‌ها برقرار باشد:

- [ ] کد پیاده شده
- [ ] تست‌ها نوشته و سبزند
- [ ] migration اجرا شده
- [ ] API مستند شده (OpenAPI)
- [ ] اسکن امنیتی بدون یافتهٔ Critical/High
- [ ] README به‌روز شده
- [ ] `.env.example` به‌روز شده
- [ ] `docker compose up` کار می‌کند
- [ ] CI سبز است
- [ ] هیچ TODOای برای عملکرد الزامی نمانده
- [ ] هیچ پیاده‌سازی placeholder نمانده
- [ ] هیچ mockای در مسیر عملیاتی نیست
