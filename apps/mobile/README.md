# آکادمی ماتریدی — Mobile App (Phase 13)

React Native mobile app (Expo managed workflow, SDK 53) for the Maturidi
Academy platform. Full module parity with the web app, driven by the same
`/api/v1` contracts.

> **Honest build note:** native binaries (APK/IPA/AAB) cannot be produced in
> this sandbox — there is no Android SDK / Xcode here. Store artifacts are
> produced with **EAS Build** (see below). No build artifact in this repo is
> faked: `android/` and `ios/` directories are intentionally **not**
> committed — they are generated by `expo prebuild` on the build machine.

## Structure

```
apps/mobile/
  app.json            Expo config (name «آکادمی ماتریدی», RTL, fa default)
  src/
    App.tsx           Root: RTL bootstrap, providers, navigator
    types.ts          Client mirror of the /api/v1 DTOs (subset)
    i18n/strings.ts   fa/ar/en strings — no hardcoded UI text (§15.4)
    lib/
      config.ts       API URL / EAS project id (env → app.json → default)
      api.ts          Central HTTP client: JWT rotation, 401→refresh→retry,
                      uniform error envelope → ApiError
      secureStore.ts  Tokens in the OS keychain/keystore (expo-secure-store)
      db.ts           SQLite schema: offline_ops queue, sync cursors,
                      kv prefs, offline caches
      sync.ts         Sync engine: push/pull vs /api/v1/sync/*, backoff,
                      tombstones, per-entity conflict policies
    services/         Business logic (auth, quran, tasbih, adhan, fatwa,
                      library, lms, social, push, settings, home)
    hooks/            UI-state orchestration over services (useAuth, useQuran…)
    screens/          Presentational screens — zero business logic (ADR-001)
    navigation/       Auth gate + bottom tabs + per-module stacks
```

Presentational components (`Button`, `Card`, `Badge`, `TextField`,
`Screen`, …) live in `packages/ui-native` and are shared per the spec
(«موبایل: از `packages/ui-native`»). Design tokens come from
`packages/design-tokens` (`tokens.ts` typed mirror).

## Quick start

```bash
cd apps/mobile
cp .env.example .env        # set EXPO_PUBLIC_API_URL to your machine's LAN IP
npm install
npx expo start              # scan the QR with Expo Go, or:
npx expo run:android        # needs Android SDK locally
npx expo run:ios            # needs Xcode (macOS)
npm run typecheck           # tsc --noEmit
```

The API base URL is resolved by `app.config.js` into `expo.extra.apiUrl`:
`EXPO_PUBLIC_API_URL` wins; for the **development** environment only, the
default is `http://localhost:8000` (on a physical device use your LAN IP,
e.g. `http://192.168.1.50:8000`; the Android emulator can use
`http://10.0.2.2:8000`). **Preview/production builds fail loudly** when no
real, non-localhost API URL is configured (audit F-09) — set it in the EAS
environment variables on expo.dev or pass it as a build-workflow input.

## EAS builds

Profiles live in `eas.json`: `development` (dev client, APK), `preview`
(internal APK), `production-apk` (internal APK — a real `.apk`, not an AAB)
and `production` (store AAB). `extra.easProjectId` is **empty on purpose**:
linking the real Expo project is the owner's step (`eas init`) — see
`docs/ops/APK_BUILD_GUIDE.md` (MOBILE-EAS-01). Image assets in `assets/`
(icon, adaptive icon, splash, notification icon) are generated from the
school emblem (`apps/web/public/logo.jpg`).

## Offline & sync

Implements the client side of the Phase-13 sync contract (ADR-0010,
`apps/api/app/modules/sync/`):

- Every mutation is written to SQLite first and appended to `offline_ops`
  (`client_op_id`, `entity_type`, `entity_id`, `op_type`, `payload`,
  `base_version`) — see `src/lib/db.ts`. Entity types are the server's
  literals: `user_ayah_note`, `user_progress`, `dhikr_daily_count`; op types
  are `upsert` / `delete`. The client never invents its own.
- `src/lib/sync.ts` pushes to `POST /api/v1/sync/push` (idempotent on
  `client_op_id`) and pulls from `GET /api/v1/sync/pull?cursor=&device_id=`
  with a single integer cursor per device (`sync:cursor` in kv). Per-op
  exponential backoff, max 8 attempts.
- Pull applies **tombstones**: `op_type: "delete"` deletes the local row.
  Entities with unpushed local ops are skipped on pull so a local edit is
  never clobbered by a stale pull.
- Conflict policy is the server's (ADR-0010): scalars (`user_progress`,
  `dhikr_daily_count`) are **max-wins** and never conflict; `user_ayah_note`
  uses optimistic versioning — on conflict the server keeps its version and
  stores the client's in `conflict_records`. The app surfaces them from
  `GET /api/v1/sync/conflicts` (both versions shown, nothing silently
  dropped) and resolves via `POST /api/v1/sync/conflicts/{id}/resolve`
  (`keep_local` | `keep_remote` | `merged`).
- Offline-created notes get real client-generated UUIDs (the server rejects
  anything else); the id survives the push.
- Tasbih counts sync as the daily aggregate (`{date}:{dhikr}` entity id);
  the per-session endpoints are used for the online UX.

## Push notifications

- `expo-notifications` config plugin is wired in `app.json` (icon + color).
- **FCM credentials are NOT in this repo**: add `google-services.json`
  (Android) / `GoogleService-Info.plist` (iOS) on the build machine or via
  EAS credentials — never commit them (`.gitignore`d, contract §3).
- `EXPO_PUBLIC_EAS_PROJECT_ID` must be set for Expo Push tokens; without it
  the app logs a warning and continues without push.
- The device token is registered at `POST /api/v1/users/me/devices`
  (Phase-13 server contract; configurable via
  `EXPO_PUBLIC_PUSH_REGISTER_PATH`).
- Channels: the app only uses the **`push`** channel. `web_push` is the web
  track's concern and is never touched here (`services/settings.ts`).
- Adhan reminders are **local** notifications (work without FCM) and respect
  the user's push opt-in.

## Fonts

The theme references `Vazirmatn` (fa), `Cairo` (ar), `Inter` (en) and
`Lalezar` (headings) — the same families the web app self-hosts. To bundle
them:

1. Place the TTF/OTF files in `apps/mobile/assets/fonts/`.
2. Register them with `expo-font` under exactly those family names at
   startup (see `packages/ui-native/src/rn-theme.ts`).

Until then the OS system font is used as a silent fallback.

## EAS builds (store artifacts)

```bash
npm i -g eas-cli

eas build:configure
```

`android/` / `ios/` native projects are generated by `expo prebuild` during
the EAS run — they are not committed.

## Release checklist

### Google Play
1. `eas build --platform android --profile production` → upload the `.aab`
   to Play Console.
2. Localise the store listing (fa/ar/en) in Play Console.
3. Complete the Data safety form (tokens in keychain, SQLite on-device).

### Apple App Store
1. `eas build --platform android --platform ios --profile production` →
   submit via EAS Submit or Transporter.
2. Fill in App Privacy (data linked to user: account id, dhikr counts).

### Cafebazaar (کافه‌بازار) — Iranian market requirement
1. Build a **signed APK** (not AAB — Bazaar distributes APK):
   `eas build --platform android --profile preview` with
   `"buildType": "apk"` in `eas.json`, or a local
   `npx expo run:android --variant release` + manual signing.
2. Sign with the **same keystore** as the Play build (keep
   `maturidi-release.keystore` out of the repo; back it up — Bazaar, like
   Play, ties updates to the signing key).
3. In the Bazaar developer panel (panel.cafebazaar.ir):
   - Package name must match `app.json` (`org.maturidi.academy`).
   - Upload the APK, fill the fa listing (title «آکادمی ماتریدی»,
     description, screenshots — fa screenshots required).
   - Bazaar requires a **privacy policy URL** and an Iranian support contact.
4. IAP (if ever added): Bazaar uses its own billing — the Play Billing
   client does not work on Bazaar builds; gate it behind a build flavor.
5. Push on Bazaar devices: FCM often works, but devices without Google
   services need a fallback — the app's adhan reminders are local
   notifications and keep working; remote push degrades gracefully
   (logged, non-blocking).
